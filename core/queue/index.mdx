title: "Queue"
description: "Durable job queues over the QPub REST API."
---

Queues are a REST product for durable background work. They are project-scoped named streams of **jobs**. Workers pull jobs, process them, then **ack** or **nack**.

Queues are **not** available on the WebSocket API. Use `QPub.Rest` or raw HTTP.

## Concepts

| Concept | Description |
|---------|-------------|
| **Queue** | Named stream with config (visibility timeout, max attempts, webhook, …) |
| **Job** | Work item with payload, status, attempts |
| **Worker** | Your process that pulls and completes jobs |

Job statuses include: `pending`, `scheduled`, `running`, `completed`, `failed`, `cancelled`, `dlq` (and related transitions as returned by the API).

## Execution profile

Queues use `execution_profile: "external"` — your workers pull via REST (or receive webhooks when configured).

## Quick example

```javascript
import { QPub } from "@qpub/sdk";

const rest = new QPub.Rest({ apiKey: process.env.QPUB_API_KEY });

await rest.queues.updateConfig("emails", {
  visibilityTimeout: "30s",
  maxAttempts: 5,
});

await rest.queues.enqueue("emails", {
  to: "user@example.com",
  subject: "Welcome",
});

await rest.queues.runWorker("emails", async (job) => {
  // send email from job.payload
  return { sent: true };
});
```

`runWorker` long-polls until you call `rest.queues.stopWorker()`.

## Permissions

Workers need `dequeue` (or `subscribe`) on the queue resource; producers need `enqueue` (or `publish`). See [Permissions](/core/auth/permissions).
